# app-6 — собственные темы приложения

Playground `themes.define`: приложение объявляет свой набор тем и не подключает
ни одной темы провайдера.

## Для чего

Провайдер `@feugene/simple-package` поставляет `light` и `dark`. В этой сборке
нет ни той, ни другой — вместо них три темы приложения: **Изумруд**, **Океан**,
**Багрянец**.

Главная мысль: **набор тем принадлежит приложению**, провайдер лишь поставляет
значения, из которых его можно собрать. До `themes.define` приложение могло
только выбрать подмножество провайдерских тем; собственная тема требовала либо
переписать все токены руками через `tokenOverrides` (и получить их все под
`:root`, где три темы схлопываются в одну), либо форкнуть провайдера.

## Что проверяет

- **`themes.define` без `themes.names`** — список тем сборки равен ключам
  `define`. Провайдерские `defaultThemes` в этом случае не смотрятся вовсе:
  приложение, объявившее свои темы, владеет списком целиком.
- **`extends: 'light'`** — тема наследует эффективные токены темы `light`
  провайдера. `light` при этом резолвится, но **в CSS не попадает**: она нужна
  только как источник значений.
- **Унаследованные токены переезжают под селектор новой темы.** Это не деталь
  реализации: останься они на селекторе базы, тема включалась бы только вместе
  с базой. Видно в `crimson` — она не трогает `--x-tokenized`, и он приходит
  туда из `light` со значением `red`.
- **`tokensRef`** — палитра `crimson` лежит в `src/themes/crimson.css`, а не в
  TS-литерале. Файл читает node-слой пресета при загрузке `uno.config.ts`;
  в клиентский бандл он не попадает.
- **Селектор по умолчанию** для темы приложения — `[data-theme="<имя>"]`.
  Атрибут, а не класс: он держит одно значение, поэтому переключение между
  тремя темами не требует вычищать классы предыдущей.
- **`label` и `colorScheme`** доезжают до манифеста, и переключатель в UI берёт
  подписи оттуда. Вторая, рукописная карта «имя → подпись» разъезжалась бы с
  конфигом молча.
- **`initial: 'auto'` без `light`/`dark`.** Имён `light`/`dark` в сборке нет, и
  контроллер выбирает стартовую тему по `colorScheme` из манифеста.

## Запуск

```bash
yarn workspace @feugene/simple-package build
yarn workspace @feugene/granular-app-6 dev
```

## Проверка

```bash
yarn workspace @feugene/granular-app-6 build
yarn workspace @feugene/granular-app-6 verify
```

Ожидания — в [`expected-css.mjs`](./expected-css.mjs). Собранный CSS содержит
ровно три блока:

```css
[data-theme=emerald]{--app-accent:#10b981;…;--x-tokenized:#34d399}
[data-theme=ocean]  {--app-accent:#0284c7;…;--x-tokenized:#0369a1}
[data-theme=crimson]{--app-accent:#e11d48;…;--x-tokenized:red}
```

Последняя строка — доказательство работы `extends`: значение пришло из темы
`light`, которой в сборке нет.

## Чего здесь намеренно нет

- **`themes.names`.** Он бы перебил `define` как источник списка: `names`
  всегда главнее. Полезно, когда тему надо объявить, но пока не включать.
- **Единственной темы под `:root`.** Приложению с одной темой достаточно
  `define: { brand: { extends: 'light', selector: ':root', … } }` — тогда тема
  активна по факту существования, и рантайм-контроллер не нужен вовсе.
- **Переопределения тем провайдера.** `define: { dark: { tokens: … } }` без
  `extends`/`selector` — это точечный мерж поверх провайдера с сохранением его
  селектора. Здесь показан противоположный, более сильный сценарий.
