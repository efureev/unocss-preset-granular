# Аудит пакета `@feugene/unocss-preset-granular`

## Роль

Ты — principal frontend-инженер (Vue 3, экосистема UnoCSS/Vite, авторство публичных
npm-пакетов и билд-тулинга). Ты проводишь глубокий технический аудит пакета
`packages/unocss-preset-granular` в монорепо `unocss-preset-granular`. Ты не чинишь —
ты исследуешь, воспроизводишь и документируешь. Любое утверждение в отчёте должно
быть подтверждено кодом, сборкой или запуском, а не впечатлением от чтения.

## Что это за проект

`@feugene/unocss-preset-granular` — UnoCSS-пресет, который собирает CSS, темы и
safelist из независимых пакетов-провайдеров по контракту `GranularProvider`.
Главная ценность продукта — **гранулярность и точность сборки**: в итоговый CSS
попадает ровно то, что запрошено (выбранные компоненты + их транзитивные зависимости,
выбранные темы, ничего лишнего), детерминированно и воспроизводимо. Каждую находку
оценивай прежде всего через эту призму: угрожает ли она точности/минимальности
результата, детерминизму порядка, честности диагностики.

## Обязательный онбординг (до любых выводов)

Прочитай в этом порядке:

2. `.claude/rules/preset-core.md` — карта слоёв и инварианты ядра. Инварианты оттуда —

3. `.claude/docs/workspace.md`, `.claude/docs/gotchas.md` — команды и известные грабли.

Затем построй собственную карту пакета: 5 экспортов (`.`, `/node`, `/contract`,
`/vite`, `/runtime`), bin `granular`, слои `src/{contract,core,fs,node-utils,runtime,

`runtime.ts`, инструменты `doctor.ts`, `cli.ts`, `explain.ts`, `why-css.ts`.

## Правила работы (нарушение обесценивает аудит)

- Пакетный менеджер — **только Yarn 1**. Никаких `npm install` / `pnpm`.
- Потребители едят `dist/`, не `src/`. Всё, что проверяешь на «живом» поведении,
  проверяй после `yarn build:all` и по содержимому `dist/`, не по исходникам.
- Ничего не чини и не рефактори. Максимум — временные скрипты-репродукции в
  scratchpad. Рабочее дерево после аудита должно быть чистым.
- Каждая находка обязана иметь воспроизведение: команда + наблюдаемый вывод, либо
  точная цепочка кода `file:line → file:line` с объяснением входа, на котором ломается.

## Оси аудита

### 1. Слои и граница browser/node
- Прогони фактическую проверку границы: `grep -o 'node:[a-z/]*' packages/unocss-preset-granular/dist/index.js`
  (и то же для `contract.js`, `vite.js`, `runtime.js`) — должно быть пусто; `node:`
  разрешён только в `dist/node.js` и `dist/bin.js`.
- Сверь таблицу слоёв из `.claude/rules/preset-core.md` с реальными импортами в `src/`:
  нет ли утечек `fs/`- или `node-utils/`-кода в browser-цепочку, циклических импортов
  между слоями, «удобных» реэкспортов, пробивающих границу.
- Exports map в `package.json`: соответствие `types`/`import`/`default` реальным файлам
  `dist/`, корректность `sideEffects: ["**/*.css"]` для tree-shaking (в `dist/` вообще
  есть `.css`? если нет — поле мертво или ошибочно), нет ли путей, резолвящихся мимо
  задекларированных условий (`require`, subpath-дыры). Проверь `npm pack --dry-run`:
  что реально уедет в реестр (не утекают ли `coverage/`, карты, лишнее).

### 2. Контракт `GranularProvider`
- `GRANULAR_CONTRACT_VERSION = 1`: где и как версия фактически проверяется? Что увидит
  автор провайдера с версией 2 или без версии — типизированную ошибку или молчание?
- Полнота валидации в `expandProviders` (`InvalidProviderError`): пустой `id`, форма
  `packageBaseUrl`, рассинхрон `cssFiles`/`cssFileAssetNames` — а что НЕ валидируется?
  Придумай 3–5 некорректных провайдеров (дубли id, самозависимость компонента,
  зависимость на несуществующий компонент, кривой URL) и проверь, падает ли резолв
  типизированной ошибкой или молча даёт мусор.
- Ошибки: всё ли из `src/core/errors.ts` несёт `providerId`/`componentName`/
  `referencedBy` в полях; нет ли голых `throw new Error` / `console.warn`-пропусков
  в FS-слое, где должна быть ошибка контракта.

### 3. Точность гранулярности (сердце аудита)
- `resolveSelection` + post-order DFS: детерминирован ли порядок компонентов при любом
  порядке объявления провайдеров? Тянутся ли транзитивные зависимости ровно один раз
  (`dedupe`)? Есть ли случай, когда в CSS попадает компонент, которого не просили?
- Приоритет мержа токенов «провайдеры → компоненты → app-overrides» — подтверди тестом
  или репродукцией, особенно на конфликте одного токена в трёх местах.
- Кэши: четыре `WeakMap`-кэша по идентичности `options`. Проверь честность инварианта
  «`resolveGranularNode`, не `resolvePresetGranular` напрямую» — есть ли в кодовой базе
  (включая `doctor`, `cli`, `explain`, `why-css`, vite-хелперы) места, вызывающие
  резолв в обход, получая вторую резолюцию мимо кэшей?
- Safelist: точен ли он (нет ли over-инклюда, убивающего смысл гранулярности)?

### 4. Темы
- Токены без `--`: как система ведёт себя, если провайдер всё же передал `--x` —
  молчаливый `----x` в CSS или диагностика? Ловит ли это `doctor`?
- Манифест тем строится из той же резолюции, что и CSS (`getGranularThemeManifest` →
  `resolveGranularNode`) — проверь по коду, что нет второго прохода.
- `materializeRefs` / `tokenDefinitionsFromCss`: круговые ссылки, ссылка на
  несуществующий токен, порядок разворачивания.
- Runtime-слой (`runtime/controller.ts`, `manifest.ts`): SSR-безопасность (обращения к
  `document`/`window` на импорте?), поведение при манифесте от другой версии пресета.

### 5. FS-слой и Vite
- `readCss`: все ли пути чтения обёрнуты в `GranularCssReadError` с контекстом и
  `cause`; `resolveScanDirs` и `buildContentFilesystem`: симлинки Yarn-workspace,
  отсутствующие каталоги, дубли путей.
- `emittedImports`, `vite-utils/cssAssets`: согласованность имён ассетов с
  `cssFileAssetNames` контракта.
- `vite.ts` заявлен как «чистые функции без node:» — подтверди по `dist/vite.js`.

### 6. Инструменты: doctor / explain / why-css / CLI
- Прогони `granular doctor` на живых провайдерах репо: ловит ли он рассинхрон
  задекларированного графа с реально собранным `dist` провайдера (его заявленная
  функция)? Согласованы ли exit codes, формат вывода и словарь диагностик между
  четырьмя инструментами, или каждый говорит на своём языке?
- `cli.ts` — 100% покрытие заявлено; проверь, что покрытие меряет поведение, а не
  строки (краевые случаи аргументов, несуществующий провайдер, пустой конфиг).

### 7. Тесты и покрытие
- `yarn test:granular` — зелёный ли базовый прогон (заявлено 290). `--coverage` —
  держатся ли пороги 90/85/90.
- Тесты объявлены авторитетной спецификацией (`docs/en/troubleshooting.md`): найди
  поведение, которое есть в коде, но не описано ни тестом, ни доками — это
  «молчаливое расхождение со спецификацией», отдельная категория находок.
- Карта дыр: какие ветки ошибок, какие комбинации опций не покрыты; e2e
  (`granularContent.e2e`) — насколько он близок к реальному пути `apps/*`.

### 8. Инфраструктура пакета
- `package.json`: `engines >=22` против фактически используемых API; `peerDependencies
  unocss ^66.7.5` — а `@unocss/preset-mini` в dev: нет ли скрытой runtime-зависимости
  на него? Runtime-зависимость `@feugene/unocss-mini-extra-rules` — оправдана ли она
  в ядре пресета или это связывание, мешающее переиспользованию?
- Сборка: `vite build && tsc` — сверь список entry в `vite.config.ts` с exports map;
  `tsconfig.build.json` против `tsconfig.json` — не расходятся ли таргеты/strict-флаги.
- Гигиена: `coverage/` лежит внутри пакета — в `.gitignore`? в `files`/`npm pack`
  не попадает? `docs/SPEC.md` — актуален ли против кода или это музей.

### 9. Документация
- `docs/en` ↔ `docs/ru` — зеркала: проверь построчную синхронность хотя бы diff-ом
  структуры. README пакета против фактического API `dist/types/`: каждый пример из
  README должен компилироваться против текущих типов.

## Формат отчёта (по-русски)

1. **TL;DR** — 5–10 строк: общее здоровье пакета, три главных риска.
2. **Суть проекта своими словами** — 1 абзац (проверка твоего же понимания).
3. **Находки**, отсортированы по серьёзности: `blocker / major / minor / nit`.
   Каждая: заголовок; серьёзность; `file:line`; воспроизведение (команда/цепочка);
   влияние на гранулярность и точность сборки; рекомендуемое направление фикса
   (без реализации).
4. **Неконсистентности** — расхождения код↔доки↔тесты↔правила `.claude/`.
5. **Оптимизации** — с оценкой выигрыша и цены (пример масштаба: резолюция на одном
   объекте опций 1 мс против 30 мс на новых — такого рода цифры, измеренные, не
   предположенные).
6. **Куда расти** — 5–7 направлений с обоснованием от главной ценности продукта.
   Рассмотри как минимум: watch/HMR-историю для авторов провайдеров (сейчас правка
   `src/` без пересборки молча ничего не меняет — главный DX-капкан репозитория);
   `granular doctor --fix` или строгий CI-режим; политика версионирования контракта
   к 1.0 (миграционные ошибки для версии 2); публичный тип-тест API (`expect-type`)
   как замок на exports map; бенчмарк-сьют резолюции в CI.

## Критерий завершения

Аудит закончен, когда: все 9 осей пройдены; каждый инвариант из
`.claude/rules/preset-core.md` имеет вердикт «подтверждён / нарушен (где) /
непроверяем (почему)»; в отчёте нет ни одного утверждения без воспроизведения;
рабочее дерево чистое.
