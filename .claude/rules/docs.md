## Зеркальность en/ru

`docs/en/*.md` и `docs/ru/*.md` — парные файлы, синхронные вплоть до номеров строк
(±2). Набор файлов одинаков: `README`, `getting-started`, `installation`,
`usage-in-apps`, `authoring-providers`, `component-authoring`, `component-scanning`,
`themes-and-tokens`, `architecture`, `troubleshooting`, `cli`.

То же для корневых `README.md` / `README.ru.md`.

Расхождение ловится проверкой — гоняй её после ЛЮБОЙ правки доков:

```bash
yarn check:docs        # node scripts/check-docs-parity.mjs
```

Сравнивается скелет, а не текст: набор файлов, последовательность уровней
заголовков, последовательность языков блоков кода, мультимножество ссылок на
`.md` (+ существование целей) и объём с допуском. Практическое следствие: в
паре должно совпадать ЧИСЛО и ПОРЯДОК блоков кода — добавил пример в `en`,
добавь и в `ru`. Якори не сравниваются (они слаги переведённых заголовков),
но сравнивается факт их наличия: ссылка на раздел в одной локали и на начало
файла в другой — расхождение.

Та же проверка стоит в CI отдельным job'ом `docs-parity` и входит в
`yarn test:all`.

## Проверять по коду, а не по соседнему абзацу

В документации разом было закрыто 10 расхождений с кодом: мёртвое поле
контракта, описанное как рабочее; опция, описанная как
«добавляет», а фактически заменявшая; дефолт, которого нет; пример с `--` в ключах
токенов, ломавший тему; механизм fallback, описанный не тем, чем он был. Все они
появились одинаково: текст писался по соседнему тексту, а не по коду. Поэтому:

- любое утверждение о поведении сверяй с исходником, а не с тем, что написано рядом;
- примеры кода в доках должны быть исполнимы дословно — их копируют;
- нашёл расхождение — чини поведение вместе с текстом; не переписывай текст под
  неверное поведение и наоборот.

## Точки, где ошибались чаще всего

- **Ключи токенов — без `--`.** Генератор дописывает префикс сам.
- **Точек входа шесть**: `.`, `./node`, `./contract`, `./vite`, `./runtime`,
  `./codegen` (последняя — оснастка провайдера, Node-only).
  `./vite` (`granularChunkFileNames`) забывают почти везде.
- **`scan.extensions` дополняет** дефолтный список расширений; заменяет —
  только вместе с `scan.replaceExtensions: true`.
- **`layer` по умолчанию `'granular'`**, и пресет сам объявляет его порядок (`-50`,
  между `preflights` и `shortcuts`). `layer: null` — без слоя вовсе. Порядок
  объявлять ОБЯЗАТЕЛЬНО: неизвестному слою UnoCSS даёт `0`, и он уезжает после утилит.
- **Короткая форма `'Name'`** в `components` не поддерживается, только в
  `dependencies` компонента.
- **Разделитель в ключе — ПОСЛЕДНЕЕ двоеточие**: `'a:b:C'` — это провайдер `a:b`.
- **`src/ ↔ dist/` «зондирования» нет**: fallback `cssFiles` — это
  `cssFileAssetNames[i]`, резолвнутый от `packageBaseUrl`.
- **Strict-режима для чтения CSS нет** — `scan.strict` только про layout-контракт
  директорий; отсутствующий CSS — это всегда жёсткая ошибка `GranularCssReadError`
  с провайдером, секцией и компонентом (сырой `ENOENT` — в `cause`).

## Нормативная спецификация

`packages/unocss-preset-granular/docs/SPEC.md` — нормативное описание контракта
версии 1 (RFC 2119): форма провайдера и дескриптора, приоритет токенов,
layout-контракт, порядок резолюции и эмиссии CSS, граница browser/node, таблица
«условие → класс ошибки». У неё нет ru-зеркала (и парити-проверка её не
трогает) — она одна, на английском, как README пакета.

Меняешь поведение ядра или контракта — правь SPEC вместе с кодом. Расхождение
между SPEC и тестами — дефект: тесты остаются исполнимой формой спецификации.
